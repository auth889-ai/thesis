# Anti-hardcode audit — 2026-09-05

Why: the supervisor believed the app was static because outputs appear instantly, models seemed to
return the same values, presets dominated, and saved results could be confused with live ones.

| gate | what was done | evidence |
|---|---|---|
| 1 Trace model id | every prediction request writes `results/runs/provenance/<run_id>.json` (run_id, city, origin, destination, dataset_hash, graph_hash, requested_model, resolved_model, checkpoint_path, checkpoint_sha256, input_window_hash, raw_prediction_hash, postprocessed_prediction_hash, start/end time, measured stages, result_source, cache_hit_training, inference_recomputed); served by `GET /api/runs/{run_id}` and `GET /api/analyze/{job}/provenance`; shown under "View technical details" | `test_gate1_provenance_record_complete` |
| 2 Models are different | same dataset, same input window (Los Angeles upload, Tue 08:00): 8 models, 8 distinct raw tensor hashes, no identical pair (STID 3f01d4e2…, GWNet 97777a4d…, STAEformer ee959db2…, DCRNN de6be6b4…, Chronos cc7dc9eb…, persistence aa052698…, HA 3ea9e2a6…, XGBoost aa1105c1…) | `pipeline/audit` run log in this file's history; provenance records an_be0798f5 (STID) vs an_3499a561 (GWNet): same dataset/graph/input hashes, different checkpoint sha and raw hashes |
| 3 Input sensitivity | automated: A origin/destination change → routes change; B modified CSV → dataset/input/raw hashes change; C STID vs GWNet → different checkpoints; D horizon 15 vs 60 → different slice; E missing checkpoint → `UNAVAILABLE`, never a number | `dashboard/backend/tests/test_anti_hardcode.py` (8 tests) |
| 4 No fake fallbacks | grep of frontend/backend: presets fill inputs only ("Try" chips); missing values now render as "—" (live twin, network panel, forecast panel, cross-city); an unavailable model raises `UNAVAILABLE: …` and the page shows the failure | this audit |
| 5 Live vs research | every response tagged: analyses and predict-lab runs `LIVE_COMPUTATION`; precomputed experiment files `RESEARCH_BENCHMARK` (banner on the Results page); chain reads with random/oracle forecasts `SYNTHETIC_WHAT_IF` | `test_gate5_precomputed_endpoints_are_tagged` |
| 6 Cache | training checkpoints cached by dataset+graph+model+config+upstream hash; every forecast recomputes inference from the current window: `cache_hit_training` and `inference_recomputed` in every result; a re-uploaded CSV invalidates the prepared data and flags models trained on the old version | modified-CSV proof: dataset 0fc9c01d… → 6da97a90…, input da6830f7… → 51931461…, raw a412fc09… → 83cb2b12…, speeds 89.4 → 58.1 km/h |
| 7 Real progress | the backend measures each stage (Resolving city, Loading graph, Validating traffic data, Loading checkpoint, Running inference, Evaluating routes, Preparing result) and the page shows the seconds; no sleeps (the only wait is the geocoder's 1 request/s policy) | screenshots below: inference 0.20 s (STID), 0.31 s (GWNet), 1.17 s (Chronos), 0.01 s (persistence) |
| 8 Random supervisor test | non-preset trips: Rangpur Medical College → Rangpur Railway Station; Nairobi Westlands → JKIA; Barcelona Sagrada Familia → Camp Nou; model comparison STID / GWNet / Chronos / persistence on the LA upload; original vs modified CSV | `screenshots/` |
| 9 Hard-code search | machine-readable audit of every displayed output field: component, endpoint, backend function, source type, run id, hardcoded=false | `output_fields_audit.json` (24 fields, 0 hardcoded) |

Bugs found and fixed by the audit: a `layers` payload for cities without history was a nested dict, which threw in the map draw and left the previous city's map on screen (looked exactly like a static page); Chronos scores inside a server thread could be recorded as zeros; a card's trust described the validation winner instead of its own model; STAEformer's GPU-logged metrics differed from its CPU evaluation (verification now uses their `evaluate.py` on the serving device).
