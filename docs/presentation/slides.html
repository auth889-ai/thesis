1 · The problem

Dhaka loses hours daily to jams — and cities act blind

  • A signal timing or diversion decision is a gamble: you can never replay the same traffic moment twice on a real road to know if it helped
  • So the science question is: how do you PROVE a traffic decision was right?
  • My answer: reconstruct the observed moment in a digital twin, freeze it, and run every action from that exact frozen state
Say: "The core contribution is a causal proof machine for traffic decisions — built from a real camera feed to a network-guarded action."

5 · Measuring — physics, not tricks

A queue is a physical fact

  • QUEUED = moving slower than half its own length per second (≈ 5–10 km/h), sustained — works on any camera, any zoom, no calibration
  • The hard case: a video that starts fully jammed. Old relative methods call it "free flow". Mine reads CONGESTED from second 0 — that is Gate 1's acceptance test
  • Unknown camera → honest "location required" — the system never invents a place

10 · Networking — how it reaches a real road

Decisions travel as V2X messages (official stack)

  • Eclipse MOSAIC 25.2 official example reproduced: 4,658 transmissions, 16,612 receptions; latency measured: median 1.9 ms
  • MOSAIC then ran our Dhaka network: hazard at Karwan Bazar → 585 vehicles broadcast → 2,593 received → 886 route switches — via messages and physics only
  • Planner actions delivered as messages with ACK: improvement holds in all 3 seeds (−4.6 / −6.7 / −1.4%)

12 · Limits — stated, not hidden

What this is not (yet)

  • Capability MODE 1 (observe/recommend); real signal command needs city authority access — the interface exists, the permission does not
  • Camera speed in m/s needs per-camera homography (queue counts do not)
  • Forecast-aware RL arms retraining after an infrastructure crash — reported as incomplete, no claim made
  • Transport model replays measured latencies; full MOSAIC-in-the-loop planner is future work
